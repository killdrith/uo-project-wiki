How to organize extensive customization

Working notes · Preferences, recommendations, and exploration retain their original status. Technical research requires version-specific verification.

WORKING RECOMMENDATION:
Keep custom game systems in clear modules where practical. Make focused core changes when a mechanic genuinely belongs in shared entity, combat, movement, or networking code. Preserve the ability to incorporate useful upstream fixes.

Examples discussed:
- Additional stats could initially belong to custom player/creature data instead of immediately changing every base Mobile.
- A universal new resource with regeneration, damage, AI interactions, and network/UI support could eventually justify deeper entity changes.
- Custom packets can communicate new statistics and progression information to the client.
- Server code remains authoritative; the client displays state and submits requests.
- Custom monster behavior is server-side, while body art, sounds, and animation frames must be available to the client.

Names such as Vitality, Wisdom, Spirit, Resolve, DragonLord, Ash Wyrm, and a "Path of the Titan" system were illustrative assistant examples. They are NOT selected features, lore, or terminology.

The conversation initially suggested using stock ClassicUO for early prototypes, then increasingly anticipated a custom client as the vision became clearer. These are compatible approaches: owning the eventual client does not require implementing every customization before a first test.
